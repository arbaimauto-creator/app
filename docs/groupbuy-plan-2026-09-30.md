## 0. 한 줄 정의

**성과가 검증된 리뷰어가 "여는 사람(호스트)"이 되어, 정해진 기간 안에 최소 수량이 모이면 공동구매가로 판매가 성사되는 기능.**
구매자는 누구나(호스트 본인 포함) 참여할 수 있고, 호스트는 홍보만 한다. 가격·물량·물류·CS·정산은 GREYD와 브랜드가 맡는다.

## 1. 현재 상태 진단 — 왜 "새로 기획"이 필요한가

코드와 문서를 확인한 결과, 공동구매라는 이름의 것이 **세 갈래로 나뉘어** 있고 서로 이어지지 않는다.

| # | 무엇 | 위치 | 상태 | 문제 |
|---|---|---|---|---|
| ① | 레거시 "글로벌 공동구매" | 앱 서버 `/videos/global-group-buying/`, `CuratedKProducts`, `VideoPageScreen`의 `isGlobalGroupBuying*` 필드 | 탐색 탭 큐레이션 섹션으로만 노출 | 앱 서버(`greyd_server`) 접근 권한이 없어 수정 불가. 최소 수량·성사 개념이 없는 "기간 할인 상품"에 가깝다. |
| ② | ops 호스트형 공동구매 (`gb-xxxx`) | ops `GroupBuy`·`GroupBuyJoin`, 앱 `Components/GroupBuyScreen.js`, `api/tracking.js` | **참여 희망(intent)까지만** 동작 | 진입이 딥링크(`greyd://groupbuy/gb-…`)뿐. 결제 버튼은 레거시 주문서(`OrderSheet`, `FEATURES.COMMERCE=false`)로 연결돼 있어 **실제로는 결제 불가**. 미달 환불·배송·정산 흐름 없음. |
| ③ | 9/20 단계형 모델 | 컨셉 문서 §2, GB-01 | 문서만 | 기존 ②는 "판매 인센티브 **또는** 공동구매" 양자택일 동의로 설계됨 → 단계형(판매 성과가 좋으면 **추가로** 공동구매 기회)으로 바꿔야 함. |

그리고 **결제 경로가 둘**이다.
- 레거시: 앱 서버 주문(`OrderSheet` → `/orders` → Stripe 패치) — 서버 패치 미적용, `COMMERCE=false`.
- 신규 스토어: ops `SellerProduct`/`StoreOrder` + Stripe Checkout (`api/store.js` `startStoreCheckout`, `screens/StoreScreen`) — 코드 있음, ops에서 동작.

### 결론 (방향)
1. **공동구매는 ② ops 호스트형을 정본으로 확장**한다. ①은 신규 개발하지 않고 대체 후 숨긴다(§8 P3).
2. **결제는 신규 스토어 경로(ops `StoreOrder` + Stripe)로 붙인다.** 레거시 `OrderSheet` 연결은 제거한다. 앱 서버 권한을 기다리지 않아도 된다.
3. 동의 모델은 9/20 단계형으로 맞춘다: 공동구매는 동의 시 고르는 혜택이 아니라 **판매 성과 이후의 별도 제안**이다.

## 2. 목표와 비목표

**목표**
- 구매자: 리뷰로 신뢰가 생긴 상품을 더 좋은 조건(공동구매가)으로 산다. 실패하면 돈이 나가지 않거나 전액 돌려받는다.
- 호스트(리뷰어): 동의·홍보만으로 추가 수익(공동구매 귀속 판매 N%)을 얻는다.
- 브랜드: 검증된 콘텐츠·수요를 근거로 물량을 확정하고 일괄 배송으로 물류비를 낮춘다.
- GREYD: 리뷰 → 구매 전환을 만드는 대표 커머스 기능.

**비목표 (이번 범위 밖)**
- 사용자가 아무 상품으로나 공동구매를 여는 "오픈형" 공동구매.
- 단계별 가격(모일수록 싸지는 티어 가격) — P3 이후 검토.
- 디지털 상품 공동구매(앱스토어 IAP 대상이 됨).
- 레거시 ① 데이터 이관.

## 4. 전체 흐름

```
[리뷰 → 2차 활용 동의 → 가공·판매 → 판매 성과 누적]           (기존 흐름)
                       │ 성과 기준 충족 (§6-1)
                       ▼
① 후보 선정 (ops 콘솔)  ─→  ② 조건 초안 (브랜드+운영: 상품·가격·최소/최대 수량·국가·기간)
                       ▼
③ 호스트 제안 (앱 알림)  ─→  호스트 수락 / 거절
                       ▼ 수락
④ 오픈 예고(선택) ─→ ⑤ 모집 OPEN ─→ 참여(희망 → 결제) ─→ 진행률 공개
                       ▼ 마감 시각
⑥ 성사 판정 ── 성사 → ⑦ 발주·3PL 일괄 배송 → ⑧ 수령 → ⑨ 정산(호스트 인센티브 확정·지급)
            └─ 미달 → 자동 취소 · (결제분) 전액 환불 · 참여자·호스트 알림
```

## 5. 핵심 결정: 결제 시점

공동구매의 설계는 "언제 돈을 받느냐"로 갈린다. 세 가지 안을 비교했다.

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| A. 즉시 결제 + 미달 환불 | 참여 = 결제. 미달이면 전액 환불 | 참여 수 = 실제 매출, 전환 손실 없음 | **Stripe는 환불해도 결제 수수료를 돌려주지 않는다** → 실패한 공구는 GMV의 약 3%가 손실. 환불 CS 부담(MoR = GREYD). |
| B. 승인만(authorize) 후 성사 시 청구 | 카드 승인만 잡고 성사 시 capture | 환불 없음, 수수료 손실 없음 | 카드 승인 유지 기간이 **최대 7일**이라 14일 모집에 못 씀. 국내 간편결제 대부분 미지원. |
| C. **참여 희망 → 성사 후 결제창** | 모집 중엔 희망(수량)만, 최소 수량 도달 시 참여자에게 결제 요청(결제 기한 내) | 환불 거의 없음, 기존 코드(참여 희망) 재사용, 앱 서버 불필요 | 희망 → 결제 **이탈**이 생긴다. 성사 판정 기준을 "결제 수량"으로 해야 함. |

**권장: P1은 C안(하이브리드), P2에서 A안을 선택 옵션으로 추가.**

C안의 구체 규칙(제안):
- 모집 기간 중: 참여 희망(수량 1~5) + **"바로 결제" 선택도 허용**(원하는 사람은 먼저 결제 → A안처럼 동작, 미달 시 환불).
- 희망 수량 + 결제 수량 ≥ 최소 수량이 되면 **"성사 임박"** 상태로 바꾸고 희망자 전원에게 결제 요청 푸시.
- 결제 기한: 요청 후 **48시간** 또는 모집 마감 중 늦은 쪽.
- **최종 성사 판정은 "결제 수량 ≥ 최소 수량"** (희망 수량은 판정에 넣지 않는다).
- 결제 기한까지 미결제 희망은 자동 소멸. 반복 미결제(3회) 계정은 희망 참여 제한.

> 이 선택이 §9-1 결정 항목 1순위다. 결정되면 §6·§7이 그대로 확정된다.

## 6. 기능 명세

### 6-1. 개설 자격 (호스트 선정)
- 대상: 2차 활용 동의가 `AGREED`이고 철회되지 않은 리뷰의 작성자.
- 기준(제안, 콘솔 설정값): 최근 30일 가공 콘텐츠 귀속 판매 **≥ 20건** 또는 귀속 매출 **≥ 100만원**.
  귀속 판매 집계가 아직 없으면(앱 서버 패치 미적용) 운영자가 콘솔에서 **수동 선정**한다.
- 한 호스트가 동시에 진행하는 공동구매는 1건.
- 공동구매 대상 상품은 ops `SellerProduct` 중 `PUBLISHED`이고 배송 가능 국가가 있는 것만.

### 6-2. 공동구매 조건 (개설 시 입력)
| 필드 | 설명 | 제안 기본값 |
|---|---|---|
| 상품 | `SellerProduct` 참조 | — |
| 공동구매가 | 정가 대비 할인가 | 정가의 70~85% |
| 최소 수량 | 성사 기준 (결제 수량) | 30 |
| 최대 수량 | 브랜드 확보 물량. 도달 시 조기 마감 | 최소 × 5 |
| 1인 최대 수량 | 되팔기 방지 | 5 |
| 판매 국가 | 배송 가능 국가 부분집합 | 1개 국가부터 |
| 오픈 예고 / 모집 기간 | 예고 시작, 모집 시작·마감 | 예고 3일, 모집 14일 |
| 배송 예정일 | 성사 후 발송 예정 | 마감 + 7일 이내 |
| 호스트 인센티브 | 공동구매 귀속 판매 N% | 5% (미확정) |
| 호스트 한마디 | 호스트가 쓰는 소개 문구(운영 검수) | 선택 |

### 6-3. 앱 — 구매자 화면
1. **발견 진입점** (지금은 딥링크뿐 → 다음을 추가)
   - 탐색 탭 "공동구매" 섹션: 진행 중·오픈 예정 카드 목록(레거시 `CuratedKProducts` 자리 대체).
   - 리뷰/쇼츠: 해당 리뷰에서 파생된 공동구매가 열려 있으면 상품 칩 옆 **"공동구매 중 · D-n"** 배지.
   - 스토어 상품 상세: 같은 상품의 공동구매가 진행 중이면 상단 배너.
   - 호스트 프로필: "진행 중인 공동구매" 카드.
2. **공동구매 상세** (`GroupBuyScreen` 확장)
   - 상단: 상품 이미지·공동구매가·정가 대비 할인율·상태 배지·남은 시간(D-n, 마지막 24시간은 시:분).
   - 진행률: **결제 수량 막대 + 희망 수량(옅은 색) 막대를 분리**해서 보여준다. "n명 참여 중" 사회적 증거.
   - 호스트 카드: 호스트 프로필·원본 리뷰 영상 바로가기·호스트 한마디.
   - 조건 박스: 판매 국가, 1인 최대 수량, 배송 예정일, "최소 수량 미달 시 자동 취소·전액 환불" 고정 문구.
   - 하단 고정 CTA(상태별 §7-2): "참여 희망 남기기" / "바로 결제" / "결제하기(기한 hh:mm)" / "알림 받기"(예고 상태).
   - 판매 국가 밖 사용자: 참여 버튼 대신 "이 국가에서도 열어주세요"(수요 신호 수집, `purchase-cta-definition` P3와 동일 테이블).
3. **내 공동구매** (마이 탭 또는 활동 탭 카드)
   - 참여한 공동구매 목록과 참여자 상태(§7-3), 결제 기한 임박 강조, 주문·배송 조회(`StoreOrders`로 연결).
4. **결제**: 신규 스토어 `startStoreCheckout`에 `groupBuyId`·`trackingCode(gb-…)`·수량을 실어 Stripe Checkout → `StoreWeb`.
   공동구매가는 **서버(ops)가 공동구매 레코드에서 계산**한다(앱이 보낸 가격을 믿지 않는다).

### 6-4. 앱 — 호스트 화면
1. **제안 수신**: 알림(신규 코드) → 제안 화면: 상품·가격·기간·국가·예상 인센티브 구조, "선정이 수익을 보장하지 않음" 고지, 수락/거절 동일 무게.
2. **공유 키트**: 공동구매 링크(`https://greyd.app/groupbuy/gb-…`), 이미지 카드, 복사/공유 시트, **광고 표기 안내**(§10-2).
3. **진행 현황**: 진행률·클릭·희망·결제 수량, 예상 인센티브(결제 기준) / 확정 / 지급 3단 구분. 기존 `SecondaryUseStatusScreen`에 탭으로 추가.

### 6-5. ops 콘솔 · 판매자 포털
- 콘솔: 후보 목록(성과순) → 조건 초안 → 호스트 제안 발송 → 개설 승인 → 진행 모니터 → **마감 판정 실행**(자동, 수동 재실행 가능) → 미달 일괄 환불 → 3PL 발주서(CSV/연동) → 송장 등록 → 정산.
- 판매자 포털: 자기 상품의 공동구매 제안 확인·물량(최대 수량) 확정, 진행 현황, 발송 정보 입력.

## 7. 상태 모델

### 7-1. 공동구매 (`GroupBuy.state`)
기존 `DRAFT|OPEN|REACHED|FAILED|SHIPPING|DONE`을 아래로 확장한다.

```
DRAFT ─(호스트 수락+운영 승인)→ SCHEDULED ─(시작 시각)→ OPEN
OPEN ─(희망+결제 ≥ 최소)→ REACHING          ※ 결제 요청 발송 상태
OPEN/REACHING ─(결제 ≥ 최대)→ CLOSED(조기 마감)
OPEN/REACHING ─(마감 시각)→ CLOSED
CLOSED ─(결제 기한 종료 후 판정: 결제 ≥ 최소)→ CONFIRMED ─→ SHIPPING ─→ DONE
CLOSED ─(결제 < 최소)→ FAILED (자동 환불)
어느 상태든 ─(운영)→ CANCELLED (브랜드 사정 등, 전액 환불)
```
- `REACHED`는 `REACHING`/`CONFIRMED` 둘로 쪼갠다. **"희망으로 채움"과 "결제로 확정"을 절대 같은 말로 표시하지 않는다**(컨셉 문서 §7 원칙).
- 판정은 멱등 잡(`groupbuy.settle.sweep`)으로 실행한다. 크론이 하루 1회라 마감 시각 정밀도가 필요하면 주기를 15분으로 줄이거나 마감 시각 트리거를 둔다.

### 7-2. 상세 화면 CTA
| 공동구매 상태 | 내 상태 없음 | 희망함 | 결제함 |
|---|---|---|---|
| SCHEDULED | 알림 받기 | — | — |
| OPEN | 참여 희망 / 바로 결제 | 희망 수정·취소 / 바로 결제 | 결제 완료 · 주문 보기 |
| REACHING | 결제하기 | **결제하기 (기한)** | 결제 완료 |
| CLOSED | 마감 | 결제 기한 내면 결제하기 | 결과 대기 |
| CONFIRMED·SHIPPING·DONE | 종료 | 참여 안 됨 | 배송 조회 |
| FAILED·CANCELLED | 종료 | 종료 | 환불 상태 |

### 7-3. 참여자 (`GroupBuyJoin.state`, 신규 필드)
`INTENT → PAYMENT_REQUESTED → PAID → (SHIPPED → DELIVERED)`, 예외 `INTENT_EXPIRED`, `CANCELLED`, `REFUND_PENDING → REFUNDED`.
주문은 `StoreOrder`와 1:1로 연결(`storeOrderId`).

## 10. 법·정책 체크리스트

1. **전자상거래법** — GREYD가 판매 주체(MoR)이므로 상세 화면에 판매자 정보, 청약철회(수령 후 7일), 교환·반품 안내를 표시한다. 미달 시 자동 취소·환불 기한(영업일 3일 이내 환불)을 명시한다.
2. **추천·보증 광고 표기** — 호스트가 대가(인센티브)를 받고 홍보하므로, 호스트 게시물에 "광고"·"유료 광고 포함" 표기가 필요하다. 공유 키트에 표기 문구를 기본으로 넣고, 앱 공동구매 상세에도 "호스트는 판매 인센티브를 받습니다"를 고지한다.
3. **가격 표시** — "정가 대비 n% 할인"의 정가는 실제 판매된 가격이어야 한다(허위 할인 표시 금지). `listPrice`는 `SellerProduct` 정가에서만 가져온다.
4. **국외 판매** — 국가별 수입 규제(화장품·식품 인증), 관세·부가세 표시(DDP/DDU) 결정.
5. **인센티브 과세** — 기존 설계 유지: 포인트 적립 시점엔 과세 없음, 현금 지급 시 원천징수.
6. **개인정보** — 배송지는 결제 시에만 수집. 호스트에게는 참여자 개인정보를 보여주지 않고 집계 숫자만 보여준다.

## 11. 단계별 출시 계획

### P1 — 결제되는 공동구매 (MVP, 앱 서버 불필요)
- ops: 상태 확장, `StoreOrder.groupBuyId`, 결제 시 가격·수량·기한 검증, 판정 잡, 미달 자동 환불(Stripe Refund), 콘솔 개설·판정·환불 화면.
- 앱: `GroupBuyScreen` 결제 경로 교체 + 상태별 CTA, 탐색 탭 공동구매 섹션, 내 공동구매, 결제 요청·성사·미달 푸시.
- 호스트 선정은 **운영 수동**, 호스트 제안은 콘솔에서 발송 → 앱은 수락 화면만.
- 1개 국가, 브랜드 직배송.
- **완료 조건**: 테스트 공동구매 1건으로 ① 성사 → 결제 → 발송 → 인센티브 확정, ② 미달 → 전액 환불을 실결제(Stripe 테스트 모드 → 소액 실결제)로 끝까지 확인.

### P2 — 호스트 경험과 성장
- 공유 키트·광고 표기, 호스트 진행 현황·예상 인센티브, 리뷰/쇼츠·상품 상세·프로필 배지, 예고(SCHEDULED)·알림 받기, 판매 국가 밖 "열어주세요" 수요 수집.
- 성과 기준 자동 후보 산정(귀속 판매 집계가 붙은 뒤).
- 즉시 결제(A안) 옵션.

### P3 — 확장
- 레거시 글로벌 공동구매(①) 섹션 교체·숨김, 다국가·3PL 연동, 국내 PG(국내 판매 시), 티어 가격, 앵콜 공동구매(성사된 건 재오픈).
