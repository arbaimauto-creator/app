# GREYD 전체 컨셉 및 기능 정의서

개발자 전달용 · 2026-09-20 · v1.1 · 단계형 인센티브 구조 반영

이 문서는 현재 소스와 기존 기획을 바탕으로 제품의 목적, 기능의 관계, 화면 구조, 개발 범위를 정리한다. **현재 확인된 사실**, **정보 구조 개선 제안**, **확정이 필요한 정책**을 구분한다. 메뉴 개선안은 아직 적용되거나 승인된 사양이 아니다. 구현 상태는 로컬 코드 기준이며, 실제 서비스의 전체 동작을 보증하는 배포 확인서가 아니다.

## 1. 먼저 이해할 한 페이지

### GREYD는 어떤 서비스인가?

**GREYD는 사람들이 실제 사용 경험으로 상품을 발견하고, 체험·구매한 경험을 리뷰로 나누며, 그 리뷰가 만든 신뢰와 성과를 보상으로 연결하는 서비스다.**

사용자는 리뷰를 보고 상품을 고를 수 있고, 체험 캠페인에 참여해 직접 리뷰를 만들 수도 있다. 판매자는 상품과 체험 기회를 제공하고, 동의를 받은 리뷰를 마케팅에 활용한다. GREYD 운영자는 참여·검수·동의·지급 과정이 제대로 이어지도록 관리한다.

### 서비스가 돌아가는 기본 흐름

```text
판매자: 상품 등록 ──→ 구매 가능한 상품 제공
         └──────→ 체험 캠페인 요청 → 운영 검토·모집
                                        ↓
사용자: 리뷰 발견 → 상품 구매 또는 체험 신청 → 사용 경험 → 리뷰 작성
           ↑                                              ↓
           └──────── 다른 사용자의 발견·신뢰 형성 ←─────────┘

리뷰 이후의 확장:
성과 있는 리뷰 → 작성자의 2차 활용 동의 → 판매자/운영의 콘텐츠 활용
             → 채널별 판매 인센티브 → 성과 검증 → 공동구매 기회·추가 인센티브
```

구매와 체험 신청은 독립적인 경로다. 상품을 구매해야만 캠페인에 참여할 수 있는 구조로 만들지 않는다. 모든 리뷰가 캠페인 리뷰인 것도 아니다.

### 우수 콘텐츠를 만든 사람에게 추가 수익 기회를 주는 구조

스폰서드·파트너스 캠페인으로 상품을 제공하고 콘텐츠를 게시하게 한다. 게시된 결과물 중 품질과 활용 가능성이 좋은 콘텐츠를 선정해 작성자에게 별도의 2차 활용 계약을 제안한다. 계약한 콘텐츠를 가공해 앱과 AppLovin 광고 등에 활용하고, 판매 채널별 귀속 실적에 따라 인센티브를 지급하는 것이 최신 사업 방향이다.

가공 콘텐츠의 실제 판매 성과가 좋으면 해당 작성자에게 공동구매를 진행할 기회를 추가로 제공한다. 공동구매와 판매 인센티브를 처음부터 양자택일하는 기존 설계는 이 단계형 모델로 변경한다. 아래 내용은 신규 사업 정의이며, 현재 코드가 모두 구현한 기능이라는 뜻은 아니다.

| 단계 | 인플루언서 | GREYD와 브랜드 | 보상 또는 기회 |
|---|---|---|---|
| 상품 제공과 제작 | 상품 사용과 콘텐츠 게시 | 상품 제공과 제작 조건 안내 | 캠페인에서 약속한 상품·기본 보상 |
| 우수 콘텐츠 선정 | 게시 콘텐츠로 평가받음 | 품질·정확성·활용 가능성 평가 | 별도 2차 활용 계약 제안 |
| 2차 활용 계약 | 범위와 조건을 확인하고 동의 | 채널·기간·편집·정산 조건 계약 | 판매 인센티브 참여 자격 |
| 가공과 판매 | 활용 내역·성과 조회 | 앱 활용 및 AppLovin 광고 등 집행 | 앱 내 귀속 판매 N%, AppLovin을 통한 Shopify 귀속 판매 N% |
| 공동구매 선정 | 추가 제안을 확인하고 참여 결정 | 가공 콘텐츠의 실제 판매 성과 평가 | 공동구매 진행 기회 |
| 공동구매 진행 | 약정한 참여·홍보 활동 수행 | 가격·물량·물류·CS·정산 운영 | 공동구매 귀속 판매 N% |

첫 번째 선정은 콘텐츠 품질과 활용 가능성, 두 번째 선정은 가공 콘텐츠의 판매 성과를 기준으로 한다. 조회수가 낮아도 좋은 콘텐츠를 만든 사람에게 첫 기회를 줄 수 있도록 평가 기준을 구분한다. 캠페인 시작부터 추가 기회의 존재를 알리되, 선정이나 수익을 보장하지 않는다. 품질 개선 효과는 실제 운영 데이터를 통해 확인한다.

기본 캠페인의 의무·보상과 추가 이용허락 계약은 분리한다. 상품 제공만으로 2차 활용에 자동 동의한 것으로 처리하지 않는다. 작성자는 추가 계약을 거절할 수 있으며, 사용 범위·보상 조건을 이해한 뒤 선택한다.

채널별 요율은 각각 설정한다. 앱 판매, AppLovin 광고를 통한 Shopify 판매, 공동구매 판매를 구분해 예상·확정·지급 금액을 보여준다. 동일 주문의 일반 판매 인센티브와 공동구매 인센티브를 중복 지급할지 여부는 미확정이다. 할인·환불·배송비·세금·광고비 반영, 귀속 기간과 복수 콘텐츠 기여 처리도 계약 전에 확정해야 한다.

AppLovin은 광고 집행 경로, Shopify는 외부 주문 발생 경로로 구분한다. 광고 소재·캠페인·계약·작성자·주문을 연결하는 추적 설계가 필요하며, 실제 지원 연동 방식과 수집 가능한 데이터는 별도 기술 검증 대상이다. 현재 자동 판매 귀속이나 정산 연동이 완성된 것으로 해석하지 않는다.

### 사용자에게 제공하는 네 가지 가치

| 가치 | 사용자가 하는 일 | GREYD가 제공하는 것 |
|---|---|---|
| 발견 | 리뷰를 보고 상품을 고른다 | 리뷰 피드, 검색, 상품 연결, 저장 |
| 경험 | 구매하거나 체험에 참여한다 | 상품·주문, 캠페인 신청, 배송·미션 안내 |
| 신뢰 | 경험을 공유하고 유용한 리뷰어를 기억한다 | 리뷰 작성, 참고 관계, 단골, 활동 신뢰 지표 |
| 보상 | 활동과 콘텐츠 활용의 결과를 확인한다 | 활동 보상, 2차 활용 동의, 인센티브·지급 이력 |

**첫 출시에서 가장 먼저 안정화할 경험:** 사용자가 체험을 신청한 뒤, 지금 할 일을 알고, 리뷰를 제출하고, 검수와 보상 결과를 확인하는 전체 과정. 구매 흐름은 별도로 결제·주문·배송까지 검증한 뒤 공개 범위를 정한다.

## 2. 누가 무엇을 사용하는가?

| 사용자 | 목적 | 주 사용 공간 | 권한의 경계 |
|---|---|---|---|
| 일반 사용자 | 상품 발견, 구매, 리뷰 열람·저장 | 사용자 앱 | 본인의 주문·저장·개인정보 |
| 리뷰 작성자·체험 참여자 | 캠페인 참여, 리뷰 작성, 보상 확인 | 같은 사용자 앱 | 본인의 신청·활동·동의·보상 |
| 판매자·브랜드 담당자 | 상품 판매, 체험 모집 요청, 리뷰 활용 | 판매자 앱 진입 + 판매자 웹 | 연결 권한이 있는 상품·캠페인·주문 |
| GREYD 운영자 | 승인, 검수, 지급 관리, 예외 처리 | 운영 웹 콘솔 | 운영 권한에 따른 관리 기능 |

일반 사용자와 리뷰 작성자를 별도 가입 유형으로 나누지 않는다. 한 사람이 구매와 리뷰 활동을 함께 한다. 판매자 화면으로 전환했다고 판매 권한이 자동 생성되지는 않는다. 서버에서 연결된 판매자 권한을 확인해야 한다.

물류사·결제사는 연계 대상이다. 현재 독립된 물류사 전용 앱이 완성된 것으로 해석하지 않는다.

## 3. 기능이 복잡해 보이는 원인과 정리 원칙

현재는 리뷰, 체험, 상품, 판매자 기능이 여러 진입점에 흩어져 있다. 기능 목록에 기존 커머스와 새 스토어가 함께 존재하고, 기획서에도 이전 정책이 남아 있다. 이를 다음 기준으로 정리한다.

1. **메뉴는 사용자의 목적에 따라 나눈다.** 체험을 찾는 곳과 이미 참여한 일을 처리하는 곳을 구분한다.
2. **진행 중인 일은 한곳에서 안내한다.** 홈에는 요약, 활동에는 실제 처리 화면을 둔다.
3. **같은 기록을 중복 생성하지 않는다.** 홈·활동·마이가 같은 활동 ID와 서버 상태를 표시한다.
4. **다른 업무의 상태는 분리한다.** 체험 상품 배송과 유료 구매 주문은 각각 관리한다.
5. **복잡한 기능은 필요한 시점에 보여준다.** 2차 활용은 요청이 있을 때, 판매자 관리는 권한 연결 후 노출한다.
6. **화면 존재·서버 연동·배포·실기기 검증을 별도로 기록한다.** 버튼이 있다는 이유만으로 완료 처리하지 않는다.

## 4. 권장 메뉴 구조 — 개선 제안

### 사용자 앱

이 앱은 구매뿐 아니라 체험 활동이 핵심이므로, 활동 탭을 유지하는 다음 4개 구조를 권장한다. 별도 쇼츠 탭은 홈의 리뷰 피드로 통합하는 안이다.

| 하단 메뉴 | 사용자가 떠올릴 질문 | 포함할 기능 | 대표 행동 |
|---|---|---|---|
| 홈 | 오늘 무엇을 보면 좋을까? | 추천 리뷰, 단골 리뷰, 추천 상품·체험, 할 일 요약 | 리뷰 보기 |
| 탐색 | 어떤 상품이나 체험이 있을까? | 리뷰·상품·체험 구분, 검색·필터, 공동구매 진입 | 상품 보기 / 체험 신청 |
| 활동 | 내가 지금 해야 할 일은? | 신청 결과, 배송·수령, 설문, 리뷰 제출, 검수, 동의 요청 | 현재 단계 처리 |
| 마이 | 내 기록과 설정은 어디 있지? | 프로필, 저장한 리뷰, 단골, 주문, 보상·지급, 주소, 설정, 판매자 센터 | 기록 확인 |

리뷰 작성은 홈·활동에서 접근 가능한 공통 작성 버튼으로 제공한다. 캠페인에서 진입하면 해당 캠페인과 상품 정보를 자동 연결하고, 일반 작성에서는 사용자가 상품을 선택한다.

알림은 처리할 화면으로 바로 연결한다. 주문은 마이에 두되 배송 상태 변경 알림에서 주문 상세로 바로 들어갈 수 있게 한다. 2차 활용 요청은 활동에서 처리하고 완료 이력은 마이에서 다시 확인한다.

### 판매자 센터

| 메뉴 | 내용 |
|---|---|
| 요약 | 검토 대기 상품, 발송할 주문, 진행 캠페인, 응답할 요청 |
| 상품 | 등록·수정·판매 상태·재고·배송 가능 국가 |
| 주문·배송 | 결제된 주문, 배송 정보, 송장 입력, 환불 상태 확인 |
| 체험 캠페인 | 모집 요청, 참여 현황, 리뷰·FGI 결과 |
| 리뷰 활용 | 2차 활용 후보, 동의 요청·범위, 가공물·성과 |
| 정산 | 판매 관련 내역과 리뷰 인센티브를 구분해 조회 |

앱은 현황 확인과 빠른 처리, 웹은 상세 입력과 관리에 중점을 둔다. 같은 업무의 이름과 상태를 통일한다. 현재 새 상품 편집은 앱에서 공통 판매자 웹을 여는 방식이므로 독립된 네이티브 편집기로 설명하지 않는다. 판매자 전체 매출 정산 자동화는 추가 정의·구현이 필요한 범위다.

### 운영 콘솔

상품 검토 / 캠페인·참여자 관리 / 리뷰 검수·FGI / 동의·공동구매 / 인센티브·지급 / 계정·알림·분석으로 업무를 묶는다. 기존 B2B 문의·계약·영업 기능은 운영·판매자 업무 안에서 보존한다.

## 6. 대표 사용자 시나리오

### A. 리뷰를 보고 구매하는 사람

1. 홈에서 리뷰를 보고 연결 상품을 연다.
2. 가격·배송 국가·배송비·재고를 확인한다.
3. 내부 구매 상품은 결제창으로, 외부몰 상품은 외부 사이트로 이동한다.
4. 내부 결제 결과는 서버 확인 후 주문에 반영한다. 확인 중이면 확인 중이라고 표시한다.
5. 마이에서 내부 주문과 배송 상태를 확인한다.

완료 기준: 동일 결제 시도가 중복 주문·재고 차감으로 이어지지 않고, 다른 계정에서 주문을 볼 수 없다. 외부몰 구매는 별도 전환 연동이 없으면 앱 주문으로 표시하지 않는다.

### B. 체험하고 리뷰를 만드는 사람

1. 탐색에서 체험 조건·기한·보상을 보고 신청한다.
2. 활동에서 선정 결과를 확인하고 배송지를 제출한다.
3. 제품 수령 후 필요한 첫인상 설문을 작성한다.
4. 사용 후 리뷰와 캠페인이 요구한 본설문을 제출한다. 인터뷰 선정자는 일정에 참여한다.
5. 검수 결과와 보상 확정을 확인하고, 지급 내역을 확인한다.

완료 기준: 앱을 종료해도 진행 상황이 유지되고, 각 단계에서 지금 할 행동을 알 수 있다. 제출·검수·지급은 각각의 상태로 보인다. 보완 요청 정책은 별도 확정한다.

### C. 상품과 체험 기회를 제공하는 판매자

1. 판매자 센터를 연결하고 상품을 등록한다.
2. 운영 검토 결과를 확인한다. 승인된 상품이 사용자 상품 목록에 나타난다.
3. 상품을 수정하면 재검토 상태가 되고, 앱과 웹에서 같은 기록을 확인한다.
4. 결제된 주문을 확인하고 송장을 입력한다.
5. 별도로 체험 캠페인을 요청하고, 운영이 게시한 캠페인의 진행 결과를 확인한다.

완료 기준: 앱과 웹이 같은 상품 ID·수정 시각·상태를 사용한다. 상품 등록이 곧 캠페인 생성이나 모집 시작을 의미하지 않는다.

### D. 리뷰의 추가 활용에 동의하는 사람

1. 자신이 만든 리뷰의 2차 활용 요청을 받는다.
2. 사용 범위와 보상 방식을 확인하고 동의 또는 거절한다.
3. 동의한 콘텐츠의 활용과 인센티브 상태를 확인한다.
4. 가공 콘텐츠의 판매 성과가 선정 기준을 충족하면 공동구매 제안을 받고, 참여 결정 후 개설 조건과 모집 결과를 확인한다.

완료 기준: 거절 경로가 있으며 동의 기록을 다시 볼 수 있다. 판매·귀속 데이터가 연결되기 전에는 실제 수익을 발생한 것으로 표시하지 않는다.

## 7. 데이터와 상태를 구분하는 기준

### 반드시 다른 기록으로 관리할 대상

| 대상 | 쉬운 정의 | 혼동하면 안 되는 대상 |
|---|---|---|
| 상품 | 판매·리뷰의 대상 | 캠페인 자체 |
| 캠페인 | 참여자를 모집하는 체험 프로젝트 | 개인의 신청 건 |
| 활동·참여 건 | 한 사람이 수행하는 캠페인 진행 기록 | 유료 구매 주문 |
| 리뷰 | 작성자가 게시한 경험 콘텐츠 | 검수 결과·사용 동의 |
| 주문 | 구매자가 결제하고 배송받는 거래 | 체험 제품 발송 |
| 2차 활용 동의 | 특정 범위의 추가 사용 허락 | 리뷰 업로드·공개 설정 |
| 보상·인센티브 | 활동 또는 성과에 따라 발생하는 혜택 | 신뢰 점수·판매자 매출 |
| 지급 | 확정 금액을 실제 지급한 기록 | 지급 예정 금액 |

### 상태 모델

| 업무 | 현재 코드의 주요 상태 또는 제품 흐름 | 표시 원칙 |
|---|---|---|
| 체험 활동 | `applied → approved → shipped → received → reviewing → done`; 예외 `cancelled`, `no_show` | 신청·선정·발송·수령·검수·완료로 안내 |
| 활동 보상 | `EXPECTED`, `REVIEWING`, `CONFIRMED`, `PAID`, `CANCELLED` | 예상과 확정, 확정과 지급을 구분 |
| 새 스토어 상품 | 등록/수정 후 `SUBMITTED`, 승인 `PUBLISHED`, 판매 중단 `ARCHIVED` 등 | 공개 가능한 상품만 구매자에게 노출 |
| 새 스토어 주문 | `PENDING → PAID → SHIPPED`; 예외 `FAILED`, `EXPIRED`, `PARTIALLY_REFUNDED`, `REFUNDED` | 배송 시작을 배송 완료로 표시하지 않음 |
| 2차 활용 동의 | 요청 → 동의/거절 → 필요 시 철회 처리 | 철회 이후 이미 배포된 콘텐츠의 처리 정책은 별도 정의 |
| 공동구매 | 초안 → 모집 → 성사/미달 → 배송 → 완료 | 희망 참여와 실제 결제, 목표 도달과 정산 완료를 분리 |

상품 검토의 거절·보완 표시 방식, 주문 취소·반품·배송 완료, 검수 보완 요청은 실제 enum과 사용자 문구를 함께 확정해야 한다. 위 표는 모든 전이가 자동화되었다는 뜻이 아니다.

### 데이터 책임

기존 앱 서버는 계정·리뷰·기존 상품/소셜 기능을 담당하고, ops 서버는 캠페인·활동·동의·보상 등 운영 업무를 담당한다. 새 스토어 연동 코드는 ops의 `SellerProduct`, `SellerAppAccess`, `StoreOrder`를 사용한다.

**기존 상품과 새 스토어 상품은 현재 동일 데이터라고 가정할 수 없다.** 리뷰에서 새 상품으로 이동하는 ID 매핑, 기존 상품 이관, 기존 주문과 신규 주문의 통합 조회는 별도 완료 조건을 세워야 한다. 공동구매·추적 인센티브도 신규 주문과 자동 연결되었다고 가정하지 않는다.

## 8. 현재 구현 상태 — 개발자가 먼저 확인할 내용

판정 기준: “코드 있음”은 구현 표면이 있다는 뜻이다. “검증 기록 있음”은 특정 테스트 결과이며, 전체 실서비스 완료와는 다르다. 이전 문서의 배포 보류 표현은 날짜가 지난 기록일 수 있다.

| 영역 | 확인된 사실 | 남은 확인·작업 |
|---|---|---|
| 핵심 앱 | 리뷰·체험·활동·프로필·보상 등의 코드와 기존 검증 기록 있음 | 실제 계정으로 전체 여정, 오류·재진입·iPhone 권한 검증 |
| 판매자 접근 | `BRAND_APP=true`; 판매자 화면과 새 스토어 연결 코드 있음 | 판매자별 권한·만료·실제 배포 버전 확인 |
| 기존 커머스 | `COMMERCE=false`; 기존 화면·API가 보존됨 | 플래그만 켜서 출시하면 안 됨 |
| 새 스토어 | 앱 5개 화면 및 ops 상품·주문·결제 연동 코드 있음 | 신규 연동 배포와 실서비스 검증은 별도 확인 필요 |
| 상품·주문 연동 검증 | 격리 DB에서 상품 공유·권한·가격·재고·결제 이벤트 테스트 통과 기록 | 실제 결제사·실제 운영 환경의 전체 흐름 미검증 |
| 결제 | Stripe Checkout·웹훅·환불 반영 코드 있음 | 키·웹훅 설정과 실제 결제/실패/환불 검증 필요 |
| 2차 활용·공동구매 | 동의·추적·참여 희망·성과 관리 코드와 기획 있음 | 신규 주문 귀속, 실제 공동구매 결제·미달 환불·물류·정산 연결 확인 |
| 단골 | 관계 API 재사용, 적중은 기기 저장; 코드 해제 기준은 2회 | 9/18 기획의 1회 이후 노출 방향과 조정 필요, 서버 동기화 필요 |
| 알림·번역 | 푸시 등록·발송 및 번역 코드 있음 | FCM 발송 설정, 정식 번역 운영 경로 확인 |
| iOS | 이전 기록상 1.99.89 빌드 234 TestFlight 제출; 신규 스토어 JS 번들 생성 통과 | 빌드 234에 이후 로컬 변경이 포함되었다고 해석하지 않음 |

초대 게이트·추천 코드·소셜 좋아요·테스트 게스트 진입은 현재 기능 플래그에서 꺼져 있다. 레퍼런스 저장·온보딩·ops 연동은 켜져 있다. 비활성 기능과 B2B 계약 기능은 코드 존재만으로 주요 메뉴에 다시 노출하지 않는다.

## 9. 확정이 필요한 정책과 충돌

| 항목 | 현재 근거 | 개발 시 처리 |
|---|---|---|
| 판매자 앱 제공 | 9/16 웹 전용에서 9/18 앱 재개방으로 변경, 현재 플래그 true | 앱 진입과 웹 관리가 함께 존재하는 기준으로 정리 |
| 단골 조건 | 코드 2회 적중, 최신 문서 1회 이후 버튼 노출 방향 | 노출 조건과 실제 관계 허용 조건을 분리해 확정 |
| 포인트·G점수 | 보상과 신뢰 지표가 함께 존재 | P는 보상, G는 활동 신뢰 지표로 설명; 현금 전환 조건 별도 확정 |
| 인센티브 | 최신 방향은 앱 판매 N%, AppLovin 경유 Shopify 판매 N%, 공동구매 N%; 과거 3%·5%·7일은 미확정 제안 | 확정 요율로 홍보하지 않음; 반품·취소 차감과 중복 귀속 정책 필요 |
| 공동구매 | 최소 수량·국가·기간·미달 환불 개념 있음 | 결제 시점·성사 판정·환불·물류 담당과 실행 방식 확정 |
| 2차 활용 | 범위·기간·국가·편집·기존 혜택 선택 구조 있음; 최신 방향은 단계형 계약 | 기존 양자택일 UI·계약·데이터를 단계형으로 변경; 기간·철회·재동의 확정 |
| 판매·정산 운영 | GREYD 판매 책임 주체 방향의 기존 기획 있음 | 실제 계약·판매국가·CS·정산 주체 확정 후 운영 문구 반영 |
| 취소·반품·보완 | 일부 상태와 운영 처리 코드 존재 | 사용자 요청 화면, 처리 담당, 기한·상태·통지 정의 |
| 기존 데이터 | 기존 서버와 ops 신규 스토어가 분리됨 | 상품 매핑·주문 통합 범위와 이관 책임자 확정 |

이 문서는 법률·세무 판단을 확정하지 않는다. 관련 항목은 제품 운영 정책의 결정 과제로만 기록한다.

## 10. 개발 우선순위와 완료 기준

### 1순위 — 구조와 기존 핵심 여정 정리

- 기능별 대표 진입점을 정하고 중복 메뉴를 연결·통합한다.
- 체험 신청부터 검수·보상 확인까지 실제 계정으로 연결한다.
- 홈·활동·마이의 같은 기록과 상태 문구를 맞춘다.
- 기존 정책 충돌과 상품 ID 연결 범위를 정한다.

### 2순위 — 판매자 앱·웹과 구매 여정 완성

- 판매자 등록/수정 → 운영 승인 → 앱 노출 → 결제 → 주문 → 송장까지 같은 데이터로 검증한다.
- 결제 실패·중복 요청·품절·판매 중단·환불·권한 만료를 확인한다.
- 실제 배포 버전과 새 iOS 빌드의 포함 기능을 기록한다.

### 3순위 — 리뷰 활용과 수익 연결

- 우수 콘텐츠 선정 → 2차 계약 → 가공물 → 앱·AppLovin 경유 Shopify 주문 귀속 → 인센티브 → 지급을 연결한다.
- 판매 성과에 따른 공동구매 자격 부여를 구현하고, 성사·미달·환불·배송·추가 인센티브 흐름을 검증한다.
- 운영 분석 데이터가 쌓인 뒤 추천과 메뉴 노출을 조정한다.

### 모든 기능에 공통인 완료 기준

1. 사용자가 진입 경로와 다음 행동을 이해한다.
2. 정상·빈 화면·로딩·오류·권한 없음 상태가 있다.
3. 뒤로가기·앱 재실행·네트워크 복구 시 기록과 진행이 유지된다.
4. 중복 탭·재요청으로 주문·참여·보상이 중복 발생하지 않는다.
5. 사용자·판매자·운영자가 같은 업무의 같은 결과를 확인한다.
6. 다른 계정·판매자의 비공개 기록은 조회하거나 변경할 수 없다.
7. 코드 테스트, 배포 확인, iOS 실기기 검증 결과를 각각 남긴다.
